# Scout additional instructions

These instructions supplement the Scout prompt for `microsoft/aspire`.
They do not expand its scope, permissions, or approval boundaries.
If they conflict with the saved prompt, follow the saved prompt.

## Turn rolling CI failures into actionable issues

1. **Start with the workflow run, not the tracker.** For a failure on `main` or the latest tracked release branch, find the recurring tracker for that workflow and branch. Look through its recent comments for the run link or commit SHA, then verify the exact run, attempt, and failed job in Actions. A tracker comment can be late, missing, or shared by multiple attempts. Do not delay an actionable failure just because the tracker has not caught up. Leave the tracker itself alone.
2. **Keep one work issue per failure cause, not per SHA.** If the failure needs work, look for a matching issue, including existing `main-ci-break` and failing-test issues. Match the affected branch and workflow, failed job or exact test, and failure signature, not the label or SHA alone. Reuse the canonical issue and add new run evidence there. If there is no matching open issue and no unresolved prior filing attempt, open a dedicated issue labeled `main-ci-break` only if the saved prompt authorizes it. Use the repository's failing-test filing path for a named test and the `[release/x.y]` title prefix for release work. Link the tracker and source runs, record the priority and why, then use the normal CIF handoff. If a create outcome is uncertain, reconcile it before trying again.
3. **Set priority from the latest comparable evidence.** Record verified transient network or runner blips without routing them. An actionable non-transient workflow failure is **P0**, as is an actionable failure whose cause or impact cannot be resolved with a quick look. A test failure that passes in a newer comparable run that actually ran the same test goes to the Worker as a suspected flake, **P1**. Multiple matching failures with comparable passes in between are evidence of a recurring flake, also **P1**. Multiple failures alone are not proof of flakiness: a test still failing consistently can be a **P0** break. A skipped test or a job that never reached it is not a pass.
4. **Close only confirmed duplicates, if authorized.** Keep the issue already being worked on; otherwise keep the oldest matching open issue. Preserve any unique evidence on the canonical issue and link it before closing an unowned, confirmed duplicate. Do not close the recurring tracker or an issue covering a different cause or additional scope. If ownership or equivalence is unclear, report it instead of closing it.
