# CI-health public report

The CI-health monitor is the only role that edits the description (body) of
`microsoft/aspire#22241`. This skill is the canonical source for that report
contract. It is a procedure, not a grant: it adds no tools, permissions,
schedules or authority.

The skill exists only on the documentation fork and is **not** available to
the upstream automation runtime. The monitor prompt therefore embeds the
contract below verbatim. A running automation must never depend on fetching
this file. Edit the contract here, re-render with
`docs/ci/automation-group/prompts/check_prompts.py --write` and re-check.
Shipping this skill upstream needs a separate PR and human merge; that does
not block an inline prompt rollout.

## Why each rule exists

- **Generated region only.** The body mixes owner-authored text with
  automation output, and every edit is attributed to the same GitHub account,
  so edit history cannot tell owner bytes from generated bytes. Markers make
  the boundary explicit; anything outside them belongs to the owner.
- **Replace, never append.** The November 15 drift (below) came from adding a
  new assessment above earlier ones and demoting the agreed layout into a
  "Historical assessment" section. History belongs in runtime artifacts.
- **Fixed shape.** Readers need the same five columns, a single human-attention
  section and at most three next steps on every pass. Detail goes into one
  bounded `<details>` block.
- **Size.** GitHub rejects bodies over 65,536 characters. The generated region
  is capped at 15,000 characters so owner content and the generated region fit
  together. Shrink the details first; the table and human-attention section are
  the last to lose content.
- **Privacy.** Claims, leases, settlement records, acknowledgements, platform
  session/run IDs and private review findings are internal coordination state.
  They stay in artifacts. Every GitHub link must point at the evidence it names.
- **Cadence.** A body edit notifies nobody, so frequent edits only add noise
  and history. Material changes publish promptly. A freshness-only edit needs
  an actual reassessment and at least three hours since the previous edit;
  changing only a timestamp is not an edit.

## Freeze and migration

The live body has no markers. Until the owner/generated boundary is
established, the monitor freezes **all** body edits, including appends. Intake,
diagnosis, repair and the rendered report artifact continue.

A boundary is established only by:

1. a body that already contains exactly one marker pair (after a migration), or
2. a pinned manager decision that cites the owner's approval, the exact body
   version (`updated_at` plus SHA-256 of the full body) and the boundary.

Never infer ownership from edit authorship, layout or position. If the
reconciliation artifact `assessment/2026-11-14/owner-report-reconciliation-complete.json`
or the prior-revision evidence cannot be read, or is ambiguous, stay frozen.

Before the first migration, archive the exact prior body losslessly:

- through the artifact chunk path (`artifact_put` with `chunks`) only if the
  chunk-upload tool is actually exposed to the run; otherwise
- as ordered parts of at most 32,768 bytes each plus a manifest listing every
  part name, byte length and SHA-256, and the SHA-256 of the whole body.

Read every part back and verify the part and whole digests before editing the
body. Never put an oversize artifact and never truncate. Then insert the
markers around the generated region named in the manager decision and replace
that region with a report in this contract's shape.

## Write and verify

1. Under the monitor lease, read the full body and `updated_at`.
2. Persist the edit intent and the prior body SHA-256.
3. Recheck the lease and the body version immediately before the edit; on any
   change, reconcile the actual body instead of assuming a single edit.
4. Edit, then reread the full body. The region must equal the rendered text and
   every byte outside it must equal the prior body. Save the receipt.

There is no installed renderer. A rendering helper may be claimed operational
only after it is actually installed and executed by the automation; until then
the monitor composes the region manually and the full post-write verification
above is the check.
